# Test Levels

## Aufgabe 1

* Diskutieren Sie: Was wird wie in ihrer Firma getestet
    * Mit welchen Test Levels hatten Sie bereits zu tun
    * Wann werden Tests ausgeführt
    * Haben Sie dedizierte Testing oder QA Teams
    * Wie sieht ihr Testing Live Cycle aus

### Firma von Nepomuk

Mit welchen Test Levels: Mit allen vier. Unit Tests und Integrationstests schreiben die Entwickler selber zusammen mit dem Feature. Mit System bzw. End to End Tests wird die ganze Applikation über das GUI getestet. Den Abnahmetest macht der Product Owner bzw. der Kunde.

Wann werden Tests ausgeführt: Bei jedem Push bzw. Pull Request läuft eine CI Pipeline mit den Tests. Wenn ein Test fehlschlägt, kann man nicht mergen. Grössere Testsuiten laufen zusätzlich in der Nacht. Vor einem Release wird die Applikation noch von Hand durchgeklickt.

QA Team: Es gibt kein eigenes Testing oder QA Team. Die Entwickler sind selber für die Tests verantwortlich, die Abnahme macht der PO bzw. der Kunde.

Testing Life Cycle: Wir arbeiten mit Scrum. Die Tests werden im Sprint zusammen mit dem Feature geschrieben. Dann gibt es ein Code Review im Pull Request, die Pipeline muss grün sein und danach wird auf der Staging Umgebung getestet. Im Sprint Review nimmt der PO das Feature ab.

Vergleich mit der Theorie: Unten bei Unit und Integration testen wie in der Theorie die Entwickler und ganz oben beim Acceptance Test der Kunde. In der Theorie macht die Integrations- und System Tests oft ein eigenes Testteam. Weil es bei uns kein QA Team gibt, machen das auch die Entwickler.

## Aufgabe 2

* Versuchen Sie folgende Begriffe einzuordnen und Abhängigkeiten untereinander zu erkennen
  * Testing approach
  * Testing levels
  * Testing types, techniques and tactics

Wir haben die Begriffe von gross nach klein eingeordnet:

```
Testing approach
 └─ Testing levels      Unit, Component, Integration, System, Acceptance
     └─ Testing types       funktional, nicht funktional, Regression
         └─ Testing techniques  Äquivalenzklassen, Grenzwerte, Code Coverage, ...
             └─ Testing tactics     manuell oder automatisiert, Tools, wann
```

### Testing approach
Der Approach ist das Vorgehen für das ganze Projekt und kommt aus der Teststrategie bzw. dem Testkonzept. Hier wird entschieden, wie viel getestet wird, ob möglichst früh getestet wird (shift left), ob man risikobasiert testet, ob mit TDD gearbeitet wird und was automatisiert wird. Daraus ergibt sich, welche Levels, Types und Techniken man überhaupt braucht.

### Testing levels
Die Levels sagen, auf welcher Stufe getestet wird: Unit, Component, Integration, System und Acceptance. Jedes Level hat ein anderes Testobjekt und meistens andere Leute, die testen. Unten sind es die Entwickler, in der Mitte Tester oder das QA Team und oben der Kunde.

### Testing types
Der Type sagt, was getestet wird. Funktional heisst, ob die Software das Richtige macht. Nicht funktional heisst, wie gut sie es macht, also Performance, Security oder Usability. Dazu kommen Regressionstests und Smoke Tests, die nach Änderungen laufen. Ein Type kann auf mehreren Levels vorkommen, z.B. Security bei Unit Tests (Eingaben prüfen) und beim System Test (Pentest).

### Testing techniques
Mit den Techniken leitet man die konkreten Testfälle ab.
- Black-Box: Äquivalenzklassen, Grenzwertanalyse, Entscheidungstabellen, Zustandsübergänge
- White-Box: Anweisungs- und Zweigüberdeckung, also Code Coverage
- Erfahrungsbasiert: Error Guessing, exploratives Testen

### Testing tactics
Die Taktik ist das praktische Wie bei der Durchführung: manuell oder automatisiert, mit welchem Tool, in welcher Reihenfolge und wann (bei jedem Commit, in der Nacht, vor dem Release). Auch welche Tests zuerst laufen, wenn wenig Zeit da ist.

### Abhängigkeiten
Der Approach legt fest, welche Levels es gibt. Pro Level wählt man die Types, die dort Sinn machen. Für jeden Type braucht man Techniken, um Testfälle zu finden, und die Taktik bestimmt am Schluss, wie diese Testfälle ausgeführt werden. Wenn man oben etwas ändert, z.B. im Approach entscheidet, alles zu automatisieren, ändert sich auch alles darunter.

Beispiel mit unserer Banken Simulation aus Unit Testing Aufgabe 4:

| Begriff | Bei der Banken Simulation |
|---|---|
| Approach | Jede Klasse wird mit automatisierten Tests abgesichert, Ziel ist eine Coverage von allen Klassen ausser Main |
| Level | Unit Test |
| Type | Funktional |
| Technique | Grenzwerte (z.B. genau bis zur Kreditlimite abheben und 1 Millirappen darüber), Code Coverage mit JaCoCo |
| Tactic | Automatisiert mit JUnit 5, läuft mit `mvn test` |

## Aufgabe 2 - JUnit Zusammenfassung

* Fassen Sie in einem Markdown-Dokument die gängigsten JUnit Features zusammen
* Erklären Sie kurze Anwendungsfälle / Beispiele für die jeweiligen Features
* Verlinken Sie eine Referenz Seite, welche Ihnen zusagt

Referenz: [JUnit 5 User Guide](https://docs.junit.org/5.11.3/user-guide/) (gleiche Version wie in unseren Projekten). Als Tutorial finden wir auch [vogella](https://www.vogella.com/tutorials/JUnit/article.html) gut.

### @Test
Markiert eine Methode als Test. Die Methode braucht keinen Rückgabewert und muss in JUnit 5 nicht mehr public sein.
```java
@Test
void addPositive() {
    assertEquals(5, calculator.add(2, 3), 0.000001);
}
```

### Assertions
Damit prüft man das Resultat. Wenn eine Assertion nicht stimmt, schlägt der Test fehl.

| Assertion | Wofür |
|---|---|
| `assertEquals(expected, actual)` | Wert vergleichen, bei double mit Delta als drittem Parameter |
| `assertTrue` / `assertFalse` | Bedingung prüfen, z.B. ob `deposit` geklappt hat |
| `assertNull` / `assertNotNull` | z.B. ob `createSalaryAccount(1)` null zurückgibt |
| `assertSame` | ob es genau das gleiche Objekt ist |
| `assertArrayEquals` | zwei Arrays vergleichen |
| `assertInstanceOf` | ob ein Objekt von einem bestimmten Typ ist |
| `assertThrows` | ob eine Exception geworfen wird |
| `assertAll` | mehrere Assertions ausführen und alle Fehler auf einmal sehen |
| `assertTimeout` | ob etwas schnell genug fertig ist |

```java
ArithmeticException e = assertThrows(ArithmeticException.class, () -> calculator.divide(5, 0));
assertEquals("Division durch 0 ist nicht erlaubt", e.getMessage());

assertAll("Grundrechenarten",
        () -> assertEquals(5, calculator.add(2, 3), 0.000001),
        () -> assertEquals(6, calculator.multiply(2, 3), 0.000001));
```

### Lifecycle: @BeforeEach, @AfterEach, @BeforeAll, @AfterAll
`@BeforeEach` läuft vor jedem Test, z.B. um ein neues Objekt zu erstellen, damit die Tests unabhängig sind. `@AfterEach` räumt danach auf. `@BeforeAll` und `@AfterAll` laufen nur einmal pro Klasse und müssen static sein, z.B. für eine Datenbankverbindung.
```java
@BeforeEach
void setUp() {
    calculator = new Calculator();
}
```

### @DisplayName
Gibt dem Test einen lesbaren Namen, der in der IDE und im Report angezeigt wird.
```java
@Test
@DisplayName("Division durch 0 wirft Exception")
void divideByZero() { ... }
```

### @Disabled
Test wird übersprungen, z.B. wenn ein Feature noch nicht fertig ist. Man sollte immer einen Grund angeben.
```java
@Disabled("Wartet auf Fix von Bug #12")
@Test
void squareRoot() { ... }
```

### @ParameterizedTest
Gleicher Test mit verschiedenen Werten, statt den Test fünfmal zu kopieren. Die Werte kommen z.B. aus `@ValueSource`, `@CsvSource` oder `@MethodSource`. Braucht die Dependency `junit-jupiter-params`.
```java
@ParameterizedTest(name = "{0} + {1} = {2}")
@CsvSource({"0, 0, 0", "10, 0, 10", "-4, -6, -10"})
void addMany(double a, double b, double expected) {
    assertEquals(expected, calculator.add(a, b), 0.000001);
}
```

### @RepeatedTest
Führt einen Test mehrmals aus, z.B. wenn man mit Zufallswerten arbeitet oder ein Test manchmal fehlschlägt.
```java
@RepeatedTest(10)
void randomNumberIsInRange() { ... }
```

### @Nested
Innere Testklassen, um Tests zu gruppieren, z.B. alle Tests für die Division zusammen.
```java
@Nested
class Division {
    @Test
    void byZero() { ... }
}
```

### @Tag
Tests markieren, damit man nur bestimmte laufen lassen kann, z.B. langsame Tests nur in der Nacht. Mit Maven: `mvn test -Dgroups=slow`.
```java
@Tag("slow")
@Test
void bigCalculation() { ... }
```

### @Timeout
Test schlägt fehl, wenn er länger braucht als angegeben (Standard in Sekunden).
```java
@Test
@Timeout(1)
void fastEnough() { ... }
```

### Assumptions
Mit `assumeTrue` wird ein Test nur ausgeführt, wenn eine Bedingung stimmt, sonst wird er übersprungen statt fehlzuschlagen. Z.B. ein Test, der nur auf dem CI Server laufen soll.
```java
assumeTrue("CI".equals(System.getenv("ENV")));
```

### @TempDir
JUnit erstellt einen temporären Ordner und löscht ihn nach dem Test wieder. Praktisch zum Testen von Code, der Dateien schreibt.
```java
@Test
void writeFile(@TempDir Path tempDir) { ... }
```

### @ExtendWith
Erweiterungen einbinden, z.B. Mockito, um Abhängigkeiten zu mocken. Das brauchen wir später bei den Schnittstellen.
```java
@ExtendWith(MockitoExtension.class)
class ServiceTest { ... }
```


## Aufgabe 3 - Banken Simulation

* Setzen Sie die Banken Simulation dementsprechend bei Ihnen lokal auf (Java / Maven Projekt)
* Studieren Sie die Software anhand des Codes und dem Klassendiagramm
* Dokumentieren Sie in Stichworten in einem Markdown-Dokument, wie die Software funktioniert und wie die Zusammenhänge sind.

Projekt: [bank](bank), Klassendiagramm in [bank/Design](bank/Design/bank6_klassendiagramm.png)

### Setup
- Maven Projekt mit Spring Boot als Parent, Spring selber wird aber nicht gebraucht, nur die Versionen der Dependencies kommen daher
- Java 19, JUnit 5
- Bauen und Tests laufen lassen: `mvn test` im Ordner `bank`
- Ohne `.idea` und Maven Wrapper übernommen, IntelliJ erkennt das Projekt über die `pom.xml`

### Einheiten
- Beträge sind `long` in Millirappen: 1 CHF = 100 Rappen = 100'000 Millirappen. Mit long gibt es keine Rundungsfehler wie bei double.
- Datum ist ein `int` mit Banktagen seit dem 1.1.1970. Ein Bankjahr hat 360 Tage, ein Monat immer 30 Tage. Beispiel: 18039 = 10.02.2020.

### Klassen
- `Bank`
  - speichert alle Konten in einer `TreeMap<String, Account>` (Kontonummer -> Konto)
  - Kontonummern: Präfix plus fortlaufende Nummer ab 1000, `S-` Sparkonto, `Y-` Jugendsparkonto, `P-` Lohnkonto
  - `createSalaryAccount` mit positiver Kreditlimite gibt `null` zurück, es wird kein Konto erstellt
  - `deposit`, `withdraw`, `getBalance(id)`, `print` arbeiten mit der Kontonummer. Bei einer unbekannten Nummer gibt es `false`, `0` oder es wird nichts gedruckt.
  - `getBalance()` ist der Saldo aus Sicht der Bank, also die Summe aller Konten negativ. Das Geld der Kunden ist für die Bank eine Schuld.
  - `printTop5` / `printBottom5` sortieren die Konten nach Saldo und drucken die ersten 5
- `Account` (abstrakt)
  - hat Kontonummer, Saldo und eine Liste von `Booking`
  - `deposit` und `withdraw` geben `false` zurück bei negativem Betrag oder wenn das Datum vor der letzten Buchung liegt (`canTransact`)
  - jede Ein- oder Auszahlung gibt eine Buchung, Auszahlungen mit negativem Betrag
  - `print()` druckt den ganzen Kontoauszug, `print(year, month)` nur einen Monat, der Saldo zählt aber die Buchungen vorher mit
  - `withdraw` prüft selber keinen Saldo, das machen die Unterklassen
- `SavingsAccount`: kein Überzug, Abheben nur bis der Saldo 0 ist
- `PromoYouthSavingsAccount`: erbt von `SavingsAccount`, bei jeder Einzahlung gibt es 1% Bonus. Weil mit Ganzzahlen gerechnet wird, gibt es unter 100 Millirappen keinen Bonus.
- `SalaryAccount`: hat eine Kreditlimite (negative Zahl), bis zu der man überziehen darf
- `Booking`: Datum und Betrag, `print(balance)` druckt eine Zeile vom Kontoauszug
- `BankUtils`: statische Methoden `formatBankDate` und `formatAmount` für die Ausgabe
- `AccountBalanceComparator` sortiert absteigend, `AccountInverseBalanceComparator` aufsteigend

### Zusammenhänge
- Eine `Bank` hat viele `Account`, ein `Account` hat viele `Booking`
- `SavingsAccount` und `SalaryAccount` erben von `Account`, `PromoYouthSavingsAccount` erbt von `SavingsAccount`
- `Bank` braucht die Comparators für Top 5 / Bottom 5
- `Booking` braucht `BankUtils` zum Formatieren

### Was uns aufgefallen ist
- `Main` erstellt ein Lohnkonto mit Kreditlimite 12000 (positiv), das gibt `null` und es wird gar kein Konto erstellt
- In `Main` steht die Frage, wie man verhindert, dass es mehr als ein `Bank` Objekt gibt: mit einem Singleton, also privatem Konstruktor und einer statischen `getInstance()` Methode
- `getBooking`/`setBooking` in `Account` und `getAccount`/`setAccount` in `Bank` werden nirgends gebraucht, das sind Überbleibsel vom UML Tool
- Das Klassendiagramm stimmt nicht ganz mit dem Code überein: in der `Bank` steht `createAccount()` statt der drei create Methoden und `SalaryAccount` hat im Code kein `print()`
- Der Javadoc Kommentar von `printBottom5` sagt "höchsten Saldo", es werden aber die tiefsten gedruckt
- Die Umlaute in den Kommentaren sind kaputt (Encoding)
- Die Comparators sind `Comparator<Object>` mit Casts statt `Comparator<Account>`


## Aufgabe 4 - Unit-Tests implementieren

Die Tests sind in `bank/src/test/java/ch/schule/bank/junit5`. Wir haben alle `fail("toDo")` aus der Vorlage ersetzt und noch ein paar Tests dazu geschrieben.

| Testklasse | Was getestet wird |
|---|---|
